# 更新時のアクセス停止

UpdateAccessは、通常処理が読み込んでいるアプリファイルやDBを、更新処理が途中で差し替えないための排他制御です。更新エンジンから利用する基盤で、更新開始/復旧の管理者入口はまだありません。

HTTP入口はautoload/config/session/DBより前に共有lockを取得し、リクエストのエラー・shutdownログが終わるまで保持します。更新のpending markerまたは排他lockがある場合は、アプリを読み込まず503を返します。日本語/English、APIのUPDATE_IN_PROGRESS、Retry-After=30、no-store、HEAD本文なしを扱います。停止中の応答はDBやApplicationLoggerへ書き込みません。静的assetはApacheから配信されるので、このlockの対象外です。

exclusiveは更新実行者の二重起動を拒否し、非公開storage/updates/access/pendingを同期書込みしたうえで新規リクエストを止めます。既存の共有lockが解放されるまで最大30秒（指定可能1〜60秒）待ってから操作を開始します。callbackが成功した場合だけ新generationを保存して停止を解除します。例外、process終了、drain timeoutは停止を残します。復旧は更新エンジンがprivate journalと保存物を確認した後にrecover=trueで行う契約です。markerを手作業で消す復旧手順は提供しません。

この状態は通常の管理画面maintenance設定と分離しています。更新終了によって管理者が設定した手動maintenanceを解除しません。更新開始をHTTP handlerの共有lock保持中に同期実行すると自分のリクエストを待ってしまうため、後続の管理者入口はjobを登録して応答を完了し、別processから更新を実行する必要があります。

PHPの手動Migration/更新確認/配布物作成/背景清掃/ログ清掃/セットアップキー作成にも停止を接続しています。定期ログ整理と更新確認は実処理・失敗ログを共有lock内で実行し、停止時はpausedとなりDBを開きません。更新後のgeneration変更を検出した定期processはrestarting/exit0で終了して新コードを読み直します。Dockerのrestart unless-stoppedが再起動を担当します。ログworkerの起動自体が停止中の場合はpaused/exit0で終了してSupervisorの再起動を待ちます。他ホストのSupervisorにもこの方針を設定する必要があります。既存sleepからの再開時にgenerationを確認するので、古いクラスのままDB処理を再開しません。

検証: 両PHPで34項目（共有/排他、二重起動、終了待ち、shutdown後の解放、process異常終了時marker保持、明示復旧、links、worker/CLIのconfig未読・非書込み）。両HTTPで30項目（GET/POST/HEAD、日英/API、DBログ・統計非書込み、通常画面復帰/config保持）。両開発環境の実workerを45秒の停止中に再起動し、paused出力とDB件数/更新metadata不変、解除後の定期処理復帰を確認しました。MariaDBの初回再起動は停止時間外だったため採用せず、再試験のpaused出力で確認しました。更新本体・journal・file/DB一括Rollbackは未接続です。任意の外部SQL、直接実行される別PHPファイル、Windows側の設定編集、静的ファイル配信、OPcacheの更新後無効化まで保証するものではありません。更新エンジンの設計でこれらの境界も確認してください。
