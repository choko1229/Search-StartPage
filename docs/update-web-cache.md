# 更新後のWeb PHPキャッシュ

public/index.phpは通常のアクセスleaseを取得した後、autoload/config/DBより前にUpdateWebCacheを呼ぶ。更新・復元・中断回復の排他終了時にUpdateAccessが進める32桁の世代を使い、同じ配置のapp/public/config/lang/database/binに属するPHPキャッシュを無効化する。CLIのopcache_resetをWebキャッシュの刷新として扱わない。

確認済みの世代はprivateなコメントだけのPHP markerをそのOPcacheへcompileして記憶する。ディスク上のmarkerだけで完了扱いにしないため、別のPHPキャッシュを持つpoolもそれぞれ刷新する。root配下でもユーザーstorageや別サイトのキャッシュは対象外。古いmarkerは清掃する。キャッシュが満杯、またはfile_update_protectionでmarkerがまだcacheに入らない場合は、次の要求で刷新を再試行する。

OPcacheが無効なら刷新は不要。OPcacheが有効なのに必要なAPIが禁止・制限されている、markerが破損・公開権限・symlinkになっている、無効化が失敗する場合は、アプリを読み込む前に既存の503更新停止応答を返す。無効化に失敗した場合はWeb側でresetを要求し、その要求ではbootstrapへ進まない。raw例外や認証情報を公開しない。

更新CLIとWebは同じユーザー・private storageを使う。最初にこのcache hookを導入する配置では、WebのPHPプロセスを再起動して、hookを持つ入口を読み込ませる。既にcacheされたhookなしの古い入口を、CLIからのファイル差替えだけで刷新できるとは扱わない。通常のreadonly開発配置に書込み権限を付けて試すことはしない。

候補互換性ではUpdateWebCacheとprotocol1を必須にし、隔離候補のcache処理を故障させたとき、実入口がconfig/DBより前に503を返すことを確認する。hookを外した候補やサービス欠落は更新前に拒否する。

検証: CLI OPcacheの日時確認を無効にした13試験、OPcache API禁止時の拒否、ネットワーク/DBなしの専用Apacheで14試験に成功。実Apacheで旧コードのcache保持を再現し、世代切替・複数Apache子・破損時停止・修復・復元を確認した。さらに専用tmpfsのMySQL8/MariaDB10.11とApacheで、実HTTP受付からworker/Engineによる適用・変更したPHP画面表示・手動復元・旧PHP画面表示まで各22試験成功。取得archiveだけfixtureを使う。

FPM、別pool同時稼働、Windows PHP、OPcache file_cache_only、実GitHub配布元による更新は未確認。Apacheの証拠をこれらへ拡張しない。サービス自動起動・常駐運用・ブラウザ実行操作・Phase9残ゲート・Version1.0最終監査も残る。
