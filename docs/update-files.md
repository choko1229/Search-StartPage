# 更新ファイルのバックアップ・差し替え・復元

UpdateFilesはUpdaterから呼ぶファイル操作の基盤です。管理画面やCLIから直接更新を開始する入口はまだありません。DBバックアップ/復元、更新ロック、書き込み停止、Migration、health検証、失敗時の自動Rollback、直前1世代への世代管理は後続の更新エンジンへ接続する必要があります。このサービス単体ではUpdater完成扱いにしません。

snapshotはReleasePackageBuilderを使い、更新前の管理対象ファイルを新規のprivate archiveへ保存します。config/config.php、storage、ユーザーアップロード、テスト用入口は含めません。VERSIONとファイルごとのハッシュを含む既存package契約を共用します。archiveは非公開ディレクトリへ作成し、更新適用と世代の切り替えが完了するまで直前のバックアップを消してはいけません。

replaceは検証済みstageと新旧manifestを受け取り、全ファイルのsize/hash、VERSION内容、allowlist、ソース・対象のリンクや不正パスを事前確認します。stageと適用先は分離したディレクトリが必要です。個々のファイルは同じディレクトリの一時ファイルへコピーして再検証し、renameで差し替えます。旧manifestにあり新manifestにないアプリファイルは削除します。追加ファイルも反映します。ユーザーデータは更新対象へ含めません。全体が単一の原子的操作になるわけではないため、後段の更新エンジンは更新ロックと書き込み停止を維持し、途中失敗した場合に必ず復元してください。

restoreは保存済みarchiveを新しいprivate stageへ検証・展開し、バックアップのmanifestへファイルを戻します。更新で増えたファイルを削除し、更新で削除されたファイルを回復します。復元stageは清掃し、清掃失敗もエラー扱いにします。DB状態やファイル外の外部副作用はこの処理では戻りません。手動・自動Rollbackの完了判定にはDB復元とアプリの動作確認が必要です。

検証: MySQL/MariaDBそれぞれのPHP環境で生成ファイルの36項目を確認。実アプリの生成コピーでは210ファイル（実配布209ファイルと削除回復用の生成1ファイル）を全ハッシュ照合して復元し、追加ファイル除去、削除ファイル回復、生成config/uploads保持、実config不変を確認しました。3ファイル目での部分失敗後にも直前の全ファイルを復元しました。改変stage、protected manifest、VERSION不一致、同じソース/対象、リンク、対象がディレクトリの場合は拒否します。本番/通常アプリへの差し替え、DB復元、自動Rollbackの実運用は未確認です。
